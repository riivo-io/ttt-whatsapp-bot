Decision Memo Queue Platform Internal Riivo / TTT Vol. 02

Stay, or migrate.

A decision memo on whether the WhatsApp bot queue should move from Upstash Redis (current production) to Azure Service Bus. Honest about what's deployed today, what would change, and what the migration actually buys.

Bot   Tina, TTT tax assistant on WhatsApp Scope today   SA tax services (insurance / accounting / FP not yet wired) Audience   Internal (Luc + TTT leadership)
Executive verdict

The short answer, before the detail.

TL;DR

Stay on the current stack. Don't migrate today.

The migration's only durable argument is consolidating identity and audit into the TTT Microsoft tenant for a future FSP audit. That's real, but it's not load-bearing yet, and every other argument in favour of Azure Service Bus is weaker than it first looks.

Per-phone FIFO, the queue feature most often cited for Service Bus, is already solved in production by 16 sharded BullMQ queues with concurrency=1 per shard, keyed by WhatsApp number. The migration would not improve message ordering. It would mostly move boxes around on an org chart.

Scope clarification Tina serves TTT's SA tax service line. The bot's tools, prompt, referral programme, and feedback flows are all tax-only. Insurance, accounting, and financial planning exist as service categories inside Dynamics 365 but the bot does not route or onboard those clients yet. Customer counts and conversation volume cited below should be read against tax-only steady state, not the full TTT book.

Where this memo lands: The current production stack works. It already does the things people most often migrate to Azure Service Bus to get. The migration's main pitch (a single Microsoft tenant for identity, billing, and audit) is true but the bot is small enough that the saved governance surface is not yet worth the engineering hours or the schedule risk on a live customer-facing channel.

This memo treats the question honestly as "should we move from production to a different stack", not as a clean greenfield bake-off. Migration cost belongs in the comparison, not in a footnote.

Capability comparison

Where the migration actually changes something.

Dimension Stay: Upstash + Fly/Railway Migrate: Azure Service Bus + Container Apps
Per-phone FIFO Solved 16 BullMQ queues, shard = hash(phone) % 16, concurrency=1 per shard. Three messages from one phone arrive at the worker in order. Solved Service Bus sessions keyed by WhatsApp number. Same outcome, different mechanism. Not a reason to move.
Idempotency Solved BullMQ jobId = wamid plus Supabase whatsapp_webhook_events unique constraint as second line. Solved ASB duplicate detection window plus the same Supabase guard. Same outcome.
Dead-letter queue In place 4 retries with exponential backoff, then drop to whatsapp_queue_dlq Supabase table. Native ASB has DLQ as a built-in subqueue. Slightly cleaner ops surface.
Identity surface Split Upstash uses a connection token. Fly.io / Railway use their own auth. Two more vendor logins for InfoSec to track. Unified ASB and Container Apps both auth via Entra ID. Same tenant as Dynamics + Graph + M365. One audit log, one RBAC model.
Compliance evidence Adequate Upstash and the worker host have SOC 2 Type II. Audit binder needs separate sections for each. Mature Azure compliance pack (ISO 27001, SOC 2, GDPR, POPIA) drops straight into an FSP audit. Less paperwork.
Data residency No SA region Upstash closest options are EU or Mumbai. Fly.io has JNB region; Railway does not. POPIA documentation needs to spell this out for queue contents (mostly wamid + phone + raw text). SA region Azure South Africa North (Johannesburg) supports Service Bus and Container Apps. Cleanest POPIA story.
Local development Excellent docker compose up with Redis is byte-identical to production semantics. No emulator drift. Decent ASB has an emulator but feature parity drifts behind the SaaS. Sessions in particular are fiddly in the emulator.
Worker timeouts Unbounded Long-running container. Mistral OCR on a dense LoE PDF, multi-turn Claude tool chains, all comfortable. Unbounded Container Apps is also long-running. Equal here.
Vendor lock-in Low Redis protocol and standard Docker. An exit ramp is an afternoon. Medium ASB SDK is portable but the feature set is Azure-flavoured. Sessions, transactions, scheduled delivery would all need replacing.
Reliability track record Solid Upstash and Fly.io both have visible incident histories. No production incidents on Tina to date. Deep Azure Service Bus is one of the oldest SaaS queues in the industry. Fewer surprises at scale.

Pros & cons of moving

What the migration actually gives and costs.

Staying on current stack

Vercel + Upstash + Fly/Railway
Where it wins
  • Zero migration cost. Already in production, handling live customer conversations.
  • Local dev parity. Docker Compose with Redis is identical to prod. Tightest iteration loop in the toolchain.
  • FIFO is already solved. Sharded BullMQ keyed by phone gives the same per-conversation ordering guarantee ASB sessions would.
  • Low lock-in. Redis protocol and Docker mean an exit ramp is short. Useful optionality.
  • Fly.io has a JHB region. Closes most of the POPIA residency gap for the worker. Upstash is still EU/Mumbai but the queue payload is small (wamid + phone + raw text).
Where it hurts
  • Two extra vendors in the InfoSec register. Upstash and the worker host both need their own contract, SOC 2 letter, and access review.
  • Upstash residency. Queue contents live outside SA. Small payloads, but the POPIA documentation has to acknowledge cross-border data flow.
  • Compliance binder is thicker. Each vendor produces its own evidence; the auditor has to read more docs.

Migrating to Azure

Service Bus + Container Apps
Where it wins
  • One Microsoft tenant. ASB, Container Apps, Dynamics, Graph, M365 all live in the same Entra ID. One audit log, one billing surface.
  • SA region for the queue. Azure South Africa North in JHB. Cleanest POPIA story for an FSP audit.
  • Mature compliance pack. Azure produces the ISO 27001 / SOC 2 / GDPR / POPIA evidence in a format auditors expect.
  • Native DLQ. Slightly cleaner than the Supabase table dance, though not a meaningful behaviour change.
Where it hurts
  • 2–4 weeks of engineering. Queue service rewrite, Bicep / Terraform for ASB, container app deployment, staged cutover on a live channel.
  • Cutover risk. The bot is live, doing real customer work. A botched migration drops messages or duplicates them. Drain and dual-write protocols add complexity.
  • Worse local dev. ASB emulator drifts behind the SaaS, especially on sessions. Docker Compose + Redis is just better.
  • Two more concepts to teach. Sessions, topics, subscriptions, SAS tokens, namespaces. New engineers ramp faster on Redis lists.
  • No FIFO win. The argument most often used to justify ASB doesn't apply because sharded BullMQ already delivers it.
  • Higher lock-in. ASB's session API is Azure-flavoured. Coming back from ASB to Redis is a project, not an afternoon.

Watch list for the current stack

Things to keep an eye on if we stay.

Stay confidently, but track these.

Items that could flip the decision later

01

POPIA documentation for cross-border queue contents.

Upstash sits in EU or Mumbai. Queue payloads are small (wamid, phone, raw message text) but they do leave SA. If an FSP audit explicitly requires SA-resident queueing for personal data, that flips the recommendation toward Azure. Worth getting in front of with legal before a reviewer asks.

02

Service scope expansion past tax.

The bot is tax-only today. If TTT wires up insurance, accounting, or financial planning flows, the bot becomes the front door for a broader regulated portfolio. That raises the bar on identity and audit, which is when the Microsoft-aligned stack starts to actually pay off.

03

Vendor count creeping into the InfoSec register.

Today: Vercel, Upstash, Fly.io / Railway, Supabase, Anthropic, Mistral, OpenAI, plus the Microsoft estate. If InfoSec pushes back on the vendor sprawl, collapsing the queue and worker into Azure becomes the cheapest win on paper.

04

Worker host pick.

Fly.io has a JHB region; Railway does not. If we settle on Railway long term, the worker compute also lives outside SA, which compounds the residency story. Locking to Fly.io for the JHB region is a small move that buys back some POPIA narrative.

Recommendation

Stay on the current stack. Revisit if the audit, the scope, or the vendor count moves.

The migration's case is real but not yet load-bearing. The bot is tax-only, the queue payload is small, and per-phone ordering is already solved. Moving today swaps a working production system for a comparable one at the cost of 2–4 weeks of engineering and live-channel cutover risk.

The trigger for revisiting is concrete:

  • An FSP auditor explicitly flags Upstash's EU/Mumbai residency for queue contents.
  • TTT wires the bot up for insurance, accounting, or financial planning, widening the regulatory surface.
  • InfoSec asks us to collapse vendors into the Microsoft estate as part of a broader tenant consolidation.

None of those are true today. When one becomes true, this memo's recommendation flips and the migration becomes a 2–4 week project, not a 6-month one. The current stack was built to be portable on purpose.
