TTT WhatsApp Bot — System Architecture

A two-process bot for TTT Financial Group, both halves on Azure App Service: clients message on WhatsApp, Meta posts to a thin web ingester that ACKs and enqueues onto Azure Service Bus, and a long-lived worker drains the queue and calls Claude with tools that read/write Dynamics, Supabase, SharePoint, and Microsoft Graph.

System overview

The web ingester stays fast and returns 200 to Meta in milliseconds; everything heavy (Claude, CRM writes, OCR, knowledge-base lookups) runs on the worker behind a per-phone FIFO queue (Service Bus sessions keyed by phone).

Why this shape

Split the ingester from the worker latency

Meta retries aggressively if the webhook doesn't return 2xx within seconds. The web App Service does the bare minimum (parse, idempotency claim, enqueue) then returns 200. The worker can take 20s on a Claude call without Meta caring.

Per-phone FIFO via Service Bus sessions ordering

A user sending three messages in a row must be processed in order — Claude sees their full context. The Service Bus session id is the phone number, so one consumer holds a phone's messages at a time while different phones run in parallel up to MAX_CONCURRENT_SESSIONS.

Dedupe = wamid, twice idempotency

Meta re-delivers on transient failures. The ingester claims the wamid in Supabase (INSERT … ON CONFLICT DO NOTHING); Service Bus also dedupes on messageId = wamid. Exhausted jobs land in whatsapp_queue_dlq.

Delayed jobs, not inline timers flow

After an L1 answer the worker enqueues a feedback-prompt job (~2.5 min) so it doesn't interrupt a still-typing client; that in turn enqueues case-auto-close (~10 min) to close silent cases. A 12h cron sweep is the fallback.

Supabase as the phone→identity cache cost

Every inbound would otherwise query Dynamics to know who's calling. Supabase caches the mapping plus session + history + intent. Dynamics edits don't propagate until npm run sync:users runs.

Two App Service apps, one queue between runtime

The web app is a thin HTTP plane (webhooks, PDF, admin); the worker app is a persistent Service Bus consumer that survives long Claude streams. The queue is the only handoff — they share no memory.

Claude does the routing, tools do the IO flexibility

Instead of a hardcoded intent classifier, the worker hands Claude a 39-tool box (get_client_invoices, get_refund_status, request_consultant_callback, …) gated by the sender's role. Claude chooses; the worker executes against Dynamics/Supabase.

Grounded answers via KB retrieval accuracy

Client/lead turns embed the message (OpenAI text-embedding-3-small) and pull the top SharePoint-KB chunks from pgvector (match_kb_chunks), injected into the prompt only when they're relevant — keeping the prompt cache warm on the common path.

A typical conversation, step by step

Sarah, an existing client, asks "Hey, has my 2024 tax refund been paid yet?"

1
Sarah taps send. WhatsApp delivers the text to Meta's Cloud servers.
Why this matters: Meta is the source-of-truth for delivery — we never poll, we wait for them to push.
2
Meta posts to our webhook with the message envelope (wamid, phone, text). The route lives in src/controllers/webhook.controller.ts on the web App Service.
3
Idempotency claim. We INSERT the wamid into Supabase; conflict means we've seen it before and silently drop.
Why: Meta retries on flaky 5xx. Without dedupe we'd answer the same question twice.
4
Enqueue on Service Bus. The message goes onto whatsapp-inbound with the session id set to Sarah's phone, so every message from her is processed in order. messageId = wamid is the second dedupe layer.
5
Return 200 to Meta. Total time so far: ~50 ms. Meta marks the message delivered and stops retrying.
6
The worker accepts the session. One slot holds Sarah's phone, so if she'd also sent a follow-up, it queues behind this one (FIFO within the session).
Why: Claude sees messages in the order Sarah sent them, not whichever finished first.
7
Load session + history from Supabase. We also resolve identity: staff? contact? lead?
8
Dynamics + KB. Pulls Sarah's contact and runs a pgvector KB retrieval on her message; both feed Claude's context.
9
Call Claude (opus-4-7) with the system prompt, conversation history, KB snippets, and a toolbox filtered by Sarah's role (clients can't run staff tools).
Why tools: the same model handles routing and response. No separate intent classifier to drift.
10–12
Tool round-trip. Claude requests get_refund_status, the worker calls Dynamics, sends the result back, Claude composes a natural-language reply (loop capped at 5 rounds).
13
Persist. Save inbound + outbound to Supabase, update intent, log token usage + any 429 telemetry against the per-session and per-day caps.
14–15
Reply via Meta send-message API. Sarah's phone buzzes.
16
Delayed feedback loop. Because Claude classified this as an L1 answer, the worker enqueues a feedback-prompt job (~2.5 min). If Sarah hasn't replied by then, the bot sends Yes/No buttons and schedules a case-auto-close job (~10 min).
Why delayed: we don't interrupt a still-typing client, and silent cases still close cleanly.

Side flow: email relay (tina-bot mailbox)

Staff forward client emails to tina-bot@ttt-group.co.za. The bot identifies the original sender, asks the matched client for consent over WhatsApp, and relays the message — without staff brokering it manually.

Two more Graph-backed flows ride the same mailbox: post-LOE activation (the Next.js signing app calls /webhook/loe-signed → Tina thanks the lead on WhatsApp and emails taxcrew the eFiling-OTP walkthrough) and the consultant close-summary (when a noteworthy session closes — a doc upload or an escalation happened — Tina emails the client's owning consultant a short Haiku-written summary, claimed once per session so a fan-out close can't double-send).

Deployment targets at a glance

Azure App Service — web plane

Hosts the Express ingester (src/server.ts), the cron-triggered sweeps (case-timeout, graph-renew), the PDF route, and the admin/template-refresh route. Thin and fast — no business logic.

Azure App Service — worker plane

Hosts the persistent Service Bus consumer (src/worker.ts). Long-running, drains three queues, runs up to MAX_CONCURRENT_SESSIONS phones in parallel. Exposes a trivial liveness endpoint only to satisfy the App Service probe.

Azure Service Bus

The work backbone. whatsapp-inbound uses sessions (session = phone) for per-phone FIFO; feedback-prompt and case-auto-close are scheduled (delayed) queues. Dedupe on messageId; up to 5 deliveries then DLQ.

Supabase

Postgres + pgvector. Holds session state, message history, cases, idempotency + DLQ tables, KB embeddings, pending LOE/IRP5 staging, and the email-relay consent table.

Note: the repo's vercel.json crons are dead on Azure — the case-timeout sweep and Graph subscription renewal must be scheduled via Azure (or an external pinger). Some code comments still reference the old BullMQ/Redis queue; the live implementation is Azure Service Bus.

What protects the system when something breaks

Meta retries (network blip)

Same wamid arrives twice → Supabase idempotency table rejects the second claim. Service Bus also dedupes the duplicate messageId. The user sees one reply.

Worker crash mid-job

Service Bus redelivers the message (the lock expires) until it succeeds or hits the max delivery count (5), after which it lands in the whatsapp_queue_dlq table and ops gets paged.

Claude rate-limited (429) or slow

The wrapper throws a typed RateLimitError; the worker re-enqueues with the retry-after delay (up to 5 attempts) before dead-lettering. The web ingester already returned 200, so Meta isn't waiting. Per-session token caps prevent runaway cost.

Dynamics is unreachable

Tool calls fail gracefully; Claude is told the tool errored and falls back to a "we'll check and come back to you" reply. A case is created so a human picks it up.

Graph subscription expires

Subscriptions live ~3 days. A scheduled cron renews them; if one lapses, the next tick recreates it idempotently (ensureSubscription).

Duplicate close emails

A "Yes" can resolve several sibling cases, and the 12h sweep can race an inbound. close_summary_sent_at is claimed atomically (update-if-NULL), so the consultant gets exactly one summary per session.

Stale phone→identity cache

Supabase caches the mapping; Dynamics edits don't propagate until npm run sync:users runs. Worth knowing when debugging "why is my message routing to the wrong role".
