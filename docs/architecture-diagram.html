TTT WhatsApp Bot — System Architecture

A hybrid Vercel + worker bot for TTT Financial Group: clients message on WhatsApp, Meta posts to a thin ingester on Vercel, jobs land in a sharded Redis queue, and a long-lived worker calls Claude with tools that read/write Dynamics, Supabase, SharePoint, and Microsoft Graph.

System overview

The ingester stays fast and returns 200 to Meta in milliseconds; everything heavy (Claude, CRM writes, OCR, knowledge-base lookups) runs on the worker behind a per-phone FIFO queue.

Why this shape

Split the ingester from the worker latency

Meta retries aggressively if the webhook doesn't return 2xx within seconds. The Vercel ingester does the bare minimum (parse, idempotency check, enqueue) then returns 200. The worker can take 20s on a Claude call without Meta caring.

Per-phone FIFO via sharded queues ordering

A user sending three messages in a row must be processed in order — Claude sees their full context. Hashing phone → shard with concurrency=1 per shard guarantees serial processing per conversation while letting different phones run in parallel.

Job ID = Meta's wamid idempotency

Meta will re-deliver the same message on transient failures. BullMQ rejects duplicate jobIds, and Supabase has a unique constraint as the second line of defense. The DLQ table catches the rest.

Supabase as the phone→identity cache cost

Every inbound message would otherwise query Dynamics to know who's calling. Supabase caches the mapping plus session + history + intent. Dynamics edits don't propagate until npm run sync:users runs.

Vercel for the HTTP plane, Fly/Railway for the worker runtime

Vercel serverless is great for thin webhook handlers and PDF generation, but can't keep a BullMQ worker warm. A persistent worker on Fly.io or Railway holds the Redis connection, runs N shards, and survives long Claude streams.

Claude does the routing, tools do the IO flexibility

Instead of writing a hardcoded intent classifier, the worker hands Claude a toolbox (get_invoices, get_refund_status, log_callback, …) gated by the sender's role. Claude chooses; the worker executes against Dynamics/Supabase.

A typical conversation, step by step

Sarah, an existing client, asks "Hey, has my 2024 tax refund been paid yet?"

1
Sarah taps send. WhatsApp delivers the text to Meta's Cloud servers.
Why this matters: Meta is the source-of-truth for delivery — we never poll, we wait for them to push.
2
Meta posts to our webhook with the message envelope (wamid, phone, text). The route lives in src/controllers/webhook.controller.ts.
3
Idempotency claim. We INSERT the wamid into Supabase; conflict means we've seen it before and silently drop.
Why: Meta retries on flaky 5xx. Without dedupe we'd answer the same question twice.
4
Enqueue on BullMQ. Shard is picked by hash(phone) % N, so every message from Sarah lands on the same shard. JobId = wamid.
5
Return 200 to Meta. Total time so far: ~50 ms. Meta marks the message delivered and stops retrying.
6
The worker picks the job. Shard-7 has concurrency=1, so if Sarah had also sent a follow-up, it queues behind this one.
Why: Claude sees messages in the order Sarah sent them, not whichever finished first.
7
Load session + history from Supabase. We also load identity: staff? contact? lead?
8
Dynamics lookup. Pulls Sarah's contact + her most recent tax requests. This becomes part of Claude's context.
9
Call Claude with the system prompt, conversation history, KB snippets, and a toolbox filtered by Sarah's role (clients can't log_callback, staff can).
Why tools: the same model handles routing and response. No separate intent classifier to drift.
10–12
Tool round-trip. Claude requests get_refund_status, the worker calls Dynamics, sends the result back, Claude streams a natural-language reply.
13
Persist. Save inbound + outbound to Supabase, update intent, log token usage against the per-session and per-day caps.
14–15
Reply via Meta send-message API. Sarah's phone buzzes.
16
Background bookkeeping. Dynamics gets a case note; if Claude classified the message as an L1 question and resolved it, the case auto-closes.
Why async: we already replied to Sarah. Logging is best-effort and shouldn't block her experience.

Side flow: email relay (tina-bot mailbox)

Staff forward client emails to tina-bot@ttt-group.co.za. The bot identifies the original sender, asks the matched client for consent over WhatsApp, and relays the message — without staff brokering it manually.

Deployment targets at a glance

Vercel — HTTP plane

Hosts the Express ingester (src/server.ts), Vercel Cron triggers (case-timeout, graph-renew-subscription), and the PDF route for invoice downloads. Cold-start tolerant, scales to zero.

Fly.io / Railway — worker plane

Hosts the persistent BullMQ worker (src/worker.ts). Long-running, holds Redis connection, runs WORKER_NUM_SHARDS shards. Sized for parallel Claude streaming.

Upstash Redis

Backing store for BullMQ. Sharded queues + dedupe on jobId. Retries 4× with exponential backoff; completed jobs aged out after 1h.

Supabase

Postgres + pgvector. Holds session state, message history, cases, idempotency table, KB embeddings, pending email relays, and the DLQ for failed jobs.

What protects the system when something breaks

Meta retries (network blip)

Same wamid arrives twice → Supabase idempotency table rejects the second insert. BullMQ also rejects the duplicate jobId. The user sees one reply.

Worker crash mid-job

BullMQ requeues automatically after the job timeout. Up to 4 attempts with exponential backoff. Then it lands in the whatsapp_queue_dlq table and ops gets paged.

Claude returns slow or 5xx

Worker retries inside the job. Vercel ingester already returned 200, so Meta isn't waiting. Per-session token caps prevent runaway cost spirals.

Dynamics is unreachable

Tool calls fail gracefully; Claude is told the tool errored and falls back to a "we'll check and come back to you" reply. Case gets created so a human picks it up.

Graph subscription expires

Subscriptions max out at ~70 hours. Vercel Cron renews every 6 hours; if it lapses, the next cron tick creates a new one. Idempotent.

Stale phone→identity cache

Supabase caches the mapping; Dynamics edits don't propagate until npm run sync:users runs. Worth knowing when debugging "why is my message routing to the wrong role".
