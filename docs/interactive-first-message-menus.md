# Interactive First-Message Menus

**Status:** design proposal — not yet implemented
**Goal:** Replace the current free-text greeting with a role-specific interactive menu sent as the first message of every new conversation (or first message after a session expires), so the user immediately sees tappable options instead of being expected to know what to ask.

---

## 1. Current state

- First-message detection already exists: [claude.service.ts](../src/services/claude.service.ts) sets `isFirstMessage = history.length === 0` and injects a role-specific greeting instruction into the system prompt.
- The greeting today is **plain text** generated by the model (e.g. *"Hey Luc! 👋 Tina here, your TTT tax sidekick..."*). No buttons, no list — the user has to type their intent.
- [meta.service.ts](../src/services/meta.service.ts) already ships three interactive helpers we can reuse as-is:
  - `sendReplyButtons(to, text, buttons[])` — up to **3** reply buttons ([meta.service.ts:72](../src/services/meta.service.ts#L72))
  - `sendListMessage(to, text, buttonText, sections[])` — up to **10** rows across sections ([meta.service.ts:276](../src/services/meta.service.ts#L276))
  - `sendFlow(...)` — structured form flow (currently only used for unknown-phone sign-up) ([meta.service.ts:221](../src/services/meta.service.ts#L221))
- Integration point: [webhook.controller.ts](../src/controllers/webhook.controller.ts) — after `resolveSender` returns the CRM entity and before the AI call, branch on `crmEntity.type` and `isFirstMessage` to emit a menu instead of (or before) the AI greeting.

## 2. Meta interactive-message constraints

Pulled from [developers.facebook.com/docs/whatsapp/guides/interactive-messages](https://developers.facebook.com/docs/whatsapp/guides/interactive-messages). These are the hard limits we have to design inside:

| Component | Limit |
|---|---|
| Reply buttons | 3 max, `title` ≤ 20 chars, `id` ≤ 256 chars |
| List rows | 10 rows max across all sections, row `title` ≤ 24 chars, `description` ≤ 72 chars |
| List button text | ≤ 20 chars |
| Body text | ≤ 1024 chars (reply buttons) / ≤ 4096 chars (list) |
| Header text | ≤ 60 chars (optional) |
| Footer text | ≤ 60 chars (optional) |

**Tap → reply shape:** a button tap sends an inbound `interactive.button_reply` with `{id, title}`; a list-row tap sends `interactive.list_reply` with `{id, title, description}`. Both are already parsed in `extractIncoming`.

## 3. Design principles

1. **One menu per type, keyed off `crmEntity.type`** — lead, client, user (staff).
2. **Menu fires once per session**, on the first inbound. Returning users in an active session should not be re-menued.
3. **"Other" = freeform handoff.** For clients and users, the last option must be an "Other" row that sets a session flag (e.g. `current_intent = 'freeform'`) and replies *"Sure — what's on your mind?"*. The next inbound is handled by the normal AI path as today.
4. **Staff menus are permission-aware.** Rows are filtered by `session.permitted_tools` so a staff member without `create_invoice` never sees "Create invoice".
5. **Menu IDs are stable and namespaced** — `menu:client:invoices`, `menu:lead:upload_docs`, `menu:user:search_client` — so the router can dispatch without string-matching titles.

## 4. Menus by user type

### 4a. Lead (prospect in onboarding)

Leads can't ask tax questions today ([claude.service.ts:807](../src/services/claude.service.ts#L807)) — their only productive action is uploading onboarding docs, so the menu is narrow and onboarding-focused. **No "Other" option** per your constraint (leads shouldn't be invited into freeform tax chat).

#### Option L1 — 3 reply buttons (recommended for v1)

```
Body: Hey {firstName}! 👋 Welcome to TTT. Let's get you set up.
      What would you like to do?

[ 📎 Upload docs ]   [ 📋 Check status ]   [ 📞 Talk to us ]
```

- IDs: `menu:lead:upload`, `menu:lead:status`, `menu:lead:callback`
- **Pros:** minimal, matches the lead's actual surface area, fits in one screen.
- **Cons:** no room to explain each option — "Check status" is vague until tapped.

#### Option L2 — list message with onboarding checklist

```
Body:   Hey {firstName}! 👋 Welcome to TTT.
Button: Start onboarding

▸ Upload ID & proof of address
▸ Upload payslips / IRP5
▸ Upload bank statements
▸ Sign Letter of Engagement
▸ Request a callback
```

- **Pros:** makes the onboarding pipeline legible; lead can see how many steps remain.
- **Cons:** implies we know which steps are already done — we don't have that per-lead state yet (noted in [leads-and-contacts.md](leads-and-contacts.md) as a gap). Building it means a `lead_onboarding_progress` table first.

#### Option L3 — reuse the existing sign-up flow

Trigger `sendFlow(...)` with `WHATSAPP_SIGNUP_FLOW_ID` on the lead's first message, same as the unknown-phone path ([webhook.controller.ts:247](../src/controllers/webhook.controller.ts#L247)).

- **Pros:** zero new infra — the flow already exists.
- **Cons:** the flow is built for collecting sign-up fields, not for picking an action. Wrong tool for this job.

**Recommendation:** L1 now, upgrade to L2 once the onboarding-progress table lands.

---

### 4b. Client (registered contact)

Clients have the widest surface area: invoices, cases, documents, consultant callback, referrals. Reply buttons (3) are too tight — a list is the right primitive. **Must include "Other"** per your constraint so clients can ask anything in freeform.

#### Option C1 — single list, 6 rows (recommended)

```
Header: TTT Financial Group
Body:   Hey {firstName}! 👋 Tina here, your tax sidekick.
        What can I help with today?
Button: Choose an option

Section: Your account
  📄 Invoices & balances        — View, download, or check what's due
  📂 Case updates               — Status on your open tax matters
  📎 Upload tax docs            — IRP5, IT3, payslips, etc.

Section: Get help
  📞 Speak to my consultant     — Request a callback
  🎁 Refer a friend             — Get your referral link
  💬 Something else             — Ask me anything
```

- IDs: `menu:client:invoices`, `menu:client:cases`, `menu:client:upload`, `menu:client:callback`, `menu:client:referral`, `menu:client:other`
- **Pros:** covers every client-facing tool in [claude.service.ts:805](../src/services/claude.service.ts#L805); descriptions tell the user what each option does without them tapping; "Something else" is the explicit freeform escape hatch.
- **Cons:** 6 rows is a lot; some users scroll past. Could split into fewer if telemetry shows low engagement on bottom rows.

#### Option C2 — 3 reply buttons + "More"

```
Body: Hey {firstName}! 👋 I'm Tina. What do you need?

[ 📄 Invoices ]   [ 📂 My cases ]   [ ➕ More options ]
```

Tapping **More options** triggers a follow-up list message with the remaining items (upload, callback, referral, other).

- **Pros:** lower cognitive load on screen 1; uses the most-common actions as the fast path.
- **Cons:** two-tap UX for the long tail; requires client-side state to know we're on "screen 2"; more code paths to maintain.

#### Option C3 — hybrid (buttons for action, list for browse)

Send reply buttons *and* a follow-up list-message offering "Browse all options". Cleaner UX on paper, but it's two messages where one would do — skip.

**Recommendation:** **C1.** Single list, descriptions do the explanatory work, one tap to any action. The "Something else" row handles your freeform requirement cleanly.

### 4c. User (staff / internal)

Staff capabilities are role-gated: a junior consultant and a senior admin see different tools ([claude.service.ts:22-46](../src/services/claude.service.ts#L22-L46)). The menu must be **filtered by `session.permitted_tools`** at send time. **Must include "Other"** per your constraint.

#### Option U1 — dynamic list filtered by permissions (recommended)

Build the row set from `permitted_tools`, grouped into sections. A full-access admin would see:

```
Header: TTT Staff
Body:   Hey {firstName} 👋 What are you working on?
Button: Pick an action

Section: Look up
  🔍 Find a client              — Search contacts by name or phone
  🔍 Find a lead                — Search my leads
  📄 Client invoices            — View balances and PDFs

Section: Create
  ➕ New lead                    — Capture a prospect
  ➕ New contact                 — Convert a lead
  ➕ New case / task             — Log work for a client

Section: Letter of engagement
  📑 Upload signed LOE          — OCR + stage for review

Section: Other
  💬 Just chat with Tina        — Ask me anything
```

- Rows are filtered: if the user lacks `send_invoice_pdf`, the "Client invoices" row is dropped; if they lack `create_lead`, "New lead" is dropped; etc.
- IDs: `menu:user:find_client`, `menu:user:find_lead`, `menu:user:invoices`, `menu:user:create_lead`, `menu:user:create_contact`, `menu:user:create_case`, `menu:user:upload_loe`, `menu:user:other`
- **Pros:** scales with the role model we already have; every staff member sees exactly what they can do; freeform escape hatch preserved.
- **Cons:** need to cap at 10 rows — if a superadmin has more than 10 permitted actions, we'll need a "More" pattern. Not a real problem today (tool count is ~10).

#### Option U2 — quick-action buttons + list fallback

```
Body: Hey {firstName} 👋 Quick actions:

[ 🔍 Find client ]   [ ➕ New lead ]   [ ➕ More / Chat ]
```

"More / Chat" triggers the full list from U1 (including "Just chat with Tina").

- **Pros:** single-tap for the 80% case (lookups and creation are the hot paths).
- **Cons:** which two actions go on the front buttons? Would vary by role — introduces another config dimension. Probably not worth it for v1.

#### Option U3 — no menu, text prompt only

Keep today's behaviour (free-text greeting with a list of capabilities). Cheaper, but it's what we're explicitly trying to move away from.

**Recommendation:** **U1.** Role-filtered list, one "Other" row to fall back into the AI.

## 5. The "Other" / freeform path

When a client or user taps the "Other" row:

1. Webhook receives `interactive.list_reply` with id `menu:client:other` (or `menu:user:other`).
2. Dispatcher recognises the `:other` suffix and:
   - Sets `session.current_intent = 'freeform'` (so we don't re-menu on the next inbound).
   - Replies with a short ack: *"Sure — what's on your mind?"* (client) / *"Go ahead — what do you need?"* (staff).
3. The next inbound is handled by the normal AI path with no special branching. The menu is **not re-sent** for the rest of the session.

For non-"Other" taps, the dispatcher maps the id directly to the corresponding tool call (e.g. `menu:client:invoices` → call `get_client_invoices` and return its output formatted by the AI). Menu taps therefore bypass intent classification — they *are* the intent.

## 6. When to re-send the menu

- **Do** send on the first inbound of a new session (matches existing `isFirstMessage` check).
- **Do** send if the session expired (30 min idle) and the user messages again — that's a new session by definition.
- **Don't** send mid-session, even if the user asks something unrelated. Once they've started typing freely, the menu would feel intrusive.
- **Don't** send to leads after they've uploaded their first onboarding doc — switch to a lighter ack.

## 7. Open questions

1. **Button text localisation.** All examples are English; the existing greeting is also English-only. If SA vernacular support is on the roadmap we should factor that in before shipping copy.
2. **Emoji in button titles** — WhatsApp renders them but they count toward the 20-char title cap. We should measure actual rendered widths on Android + iOS before committing to the emoji-heavy versions above.
3. **Telemetry.** We should log every menu tap to `sessions.messages` with the id so we can see which options are dead weight after a few weeks.
4. **Interaction with the L1 feedback buttons.** Today, after an L1 answer, we send Yes/No buttons ([webhook.controller.ts:361](../src/controllers/webhook.controller.ts#L361)). Those are unaffected — the first-message menu only fires at session start.
5. **Lead menu re-send after partial onboarding.** If a lead uploads one doc and comes back two days later (new session), do they see the same menu, or a shorter "continue where you left off" version? Depends on whether we build the progress table from §4a/Option L2.

## 8. Suggested rollout

1. Ship **C1** (client list) first — biggest surface area, highest traffic, clear ROI. Feature-flag it so we can A/B vs. today's text greeting.
2. Ship **L1** (lead buttons) next — small change, narrow scope, easy to validate.
3. Ship **U1** (staff list) last — needs the permission-filtering code path, slightly more plumbing.
4. After ~2 weeks of telemetry, revisit row ordering and whether any rows should be dropped or promoted to reply buttons.
